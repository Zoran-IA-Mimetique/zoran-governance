# Operating contract

## Pipeline

Run only the surfaces applicable to the sealed mission, but never silently omit a required surface:

`activation → prompt/content trust boundary → pre-chat → ZMOS recall and trace resolution → bounded external source lookup when required → semantic speech round trip and exact output identity → intrinsic claim/evidence/Wikimedia gate → semantic decomposition/non-conflation → frames → proxies → sources → signed phenomenal-resource search → phenomenal trajectory/causal benefit → signed host-truth gate → hard laws → polymorphic families/17-family tolerances/Progress Guard → robot handoff → K3 POST → Terminal Controller → semantic speech replay → signed session display or signed robot promotion`

An upstream failure cannot be compensated by a downstream score.

`ZoranRuntime.pre_chat()` and `ZoranRuntime.evaluate()` expose bounded stages. The separate host session authority chains 18 exact PASS receipts and signs the mission, prompt, output, validity window and chain head. `HostSessionGuard` pins that authority and rejects caller trust registries. The runtime binds the claim, semantic, phenomenal-resource, phenomenal-coherence, host-truth and robot gates to the exact receipts it computes. A deployment host must execute each stage; the signed chain authenticates the supplied execution receipts but does not make unobserved external effects true.

## Preflight

Record the exact objective and digest, declared scope, granted permissions, expected outputs and tests, required frames/proxies/sources/laws/terminal controls, rollback artifact, and host capabilities awaiting trace.

## Frames, proxies, and sources

Frame selection must be deterministic and receipts must bind the selected inputs. Every required proxy has a definition, measured value, unit, provenance, and time. The complete resource round requires a pinned host signature. Missing data is never replaced with zero. One incomplete first search authorizes exactly one `RETRY` over new resources; a second incomplete search returns `VETO`, `GYROPHARE_TRACE_ABSENTE_APRES_DEUX_RECHERCHES`, `HALLUCINATION_BLOQUANTE_OU_PHENOMENE_INEXISTANT`, and `RETOUR_ENVOYEUR`.

Source claims require unique IDs, timezone-aware timestamps, measured quality, and traceable provenance parents. A derivative and its parent share one provenance root. Contradictions for the same normalized claim are vetoes unless explicitly routed to a contested-output workflow.

Bounded-truth states are `BOUNDED_TRUTH_STRONGLY_SUPPORTED`, `BOUNDED_TRUTH_SUPPORTED`, `BOUNDED_TRUTH_PROVISIONAL`, `BOUNDED_TRUTH_CONTESTED`, and `RETRY`. Preprints remain preprints. Distinct content digests are necessary anti-aliasing evidence, not sufficient proof of institutional independence.

## Tolerances and hard laws

The historical core contains 17 families: métier, coherence, semantic, factual, numeric, measurement, temporal, source, ambiguity, causal, safety, regulatory, resource, repeatability, integration, intentional, and epistemic.

Each family is either applicable or excluded with a reason. Policies and hard contracts are copied and sealed before validation. Non-finite values and post-validation mutation cannot pass. Zero-tolerance dimensions veto any non-zero drift. Soft dimensions remain subject to local, per-dimension, métier, frame, and global caps without refunds or cross-dimension compensation.

## Phenomenal coherence

The phenomenal gate is mandatory before sources, laws, action gating, terminal validation, ZMOS validation, or robot promotion can produce a final `PASS`. It uses the six-frame, three-state, causal-benefit and exceptional-regression contract in [phenomenal-coherence.md](phenomenal-coherence.md). The historical 17-family score cannot compensate its failure or absence.

## Semantic non-conflation

The intrinsic claim gate runs first so a caller label cannot hide an object/material contradiction. Public and lexical facts require a signed Wikimedia first pass and source reliability beacon. The semantic gate then binds every source clause to exact actors, objects, modalities, required actions, forbidden actions, discriminants and falsifiers. No rule transfers between concepts without proved equivalence. See [semantic-non-conflation.md](semantic-non-conflation.md).

The claim-evidence gate then binds every output unit to its semantic receipt and exact evaluated output. Assertions require verified exact spans; unknown, stale or contested claims require explicit abstention. See [claim-evidence-and-session.md](claim-evidence-and-session.md).

Robot validation uses the separate state machine in [robot-handoff.md](robot-handoff.md). External authority does not imply omitted handoff; a proven non-applicability may pass ordinary evaluation but can never satisfy promotion.

## Progress and recovery

Progress Guard blocks repeated state/action pairs, stagnation, regression, insufficient gain/cost, and excessive cycles. A zero-immediate-gain action is admissible only inside a pre-registered, indispensable, bounded batch with measurable total gain.

The host must preserve and resubmit the complete trusted `ProgressHistoryEntry` sequence. Atomic-bundle entries carry bundle and step identities; replayed or out-of-order steps cannot pass when that history is present. Omitted or caller-forged history is an integration trust gap, not proof of fresh progress.

After `RETRY`, name the responsible actor (`LLM`, user, or connector), the exact missing condition, the smallest permitted repair, the remaining search budget, and whether the complete cycle must be replayed. After `VETO`, name the violated invariant and the return-to-sender condition. Never loop indefinitely.

## Read progress

For finite addressable objects (pages, chunks, files, rows, or equivalent units), count unique units actually read. Unknown totals remain `RETRY`. If complete reading is required and progress is below 100%, show the measured percentage and offer exactly `GO`. The terminal controller cannot validate completion without the 100% receipt.

## Terminal controller

The LLM cannot self-declare completion or promotion. The controller expects declarations and receipts for activation, ZMOS pre-retrieval, ZMOS trace-resolution applicability, K3 PRE, candidate 17-family gate, the exact runtime-generated semantic-speech, claim-evidence, semantic-non-conflation, phenomenal-resource, phenomenal-coherence, host-truth and robot-handoff gates, K3 POST, ZMOS post-append, required tests, and required external alarm surfaces.

Even a surface marked not applicable must be observed and carry a valid receipt explaining that determination. Missing, duplicate, invalid, or unobserved controls cannot pass. Extra required controls receive the same status validation as core controls. Silence of an alarm is not evidence of PASS.

`trusted_receipts` is a host trust root, not evidence merely because the caller supplied a second matching string. A secure integration must populate it from receipts emitted by executed components or verified signatures. The runtime owns the semantic-speech, semantic-non-conflation, claim, phenomenal and robot-handoff bindings. Final display reruns the semantic-speech gate, requires byte-identical output, then requires the pinned session certificate; release promotion requires the pinned dual-robot certificate.

## Delivery review

Complex deliveries require execution, objective conformity, multiframework coherence, code quality, coherence quality, evidence completeness, and review separation. Each check binds the exact objective digest, frames, and an evidence receipt. Scope paths are safe and complete. Defect counts are non-negative integers; negative values and booleans are invalid and cannot compensate positive defects.

Distinct builder/reviewer labels are only a structural separation check. Independent human or organizational review remains `RETRY` until externally attested.
